## 3. 比較対象（完了条件: OSS 事例を最低2つ比較）

動画では代表例を絞る。採用は次の2つ、LLVM を予備とする。

- **Git**: 内容アドレス型オブジェクトストアと packfile による保存・転送
- **nginx**: 少数 worker が非同期イベントループで多数接続を処理する構成

予備: **LLVM**（IR を中心にした多段変換パイプライン）。Hadoop は分散ストレージの話が中心で、本シリーズの「測定対象」の比較軸と噛み合うかを要判断のため除外候補とする。

## 4. 設計判断 → 観測対象（完了条件: 明示）

設計判断の内容は本文未読のため、以下は「一般的に知られている構造からの仮説」であり、章の確認後に確定する。

| OSS | 設計判断（仮説） | 観測対象（測るべき構造） | 観測方法（案） |
|---|---|---|---|
| Git | 内容ハッシュで不変オブジェクトを保存し、重複を共有する | オブジェクト数、重複率、packfile 圧縮率 | `git count-objects -v`、`git verify-pack` の出力 |
| Git | 履歴をグラフ（DAG）として扱う | 親の数、マージ深さ、到達可能オブジェクト数 | `git rev-list --count`、`git fsck` |
| nginx | worker 数をコア数に合わせ、接続をイベント駆動で多重化する | worker ごとの接続数、イベント待ち時間、ブロッキング有無 | `nginx -T`、stub_status、ワーカーごとの CPU 使用率 |
| nginx | 設定ファイルで挙動を宣言する | 設定の有効値（ハードコード値との差） | `nginx -T` の出力を正本として比較 |

設計判断から観測対象を導く共通の型は次のとおり。

1. 設計判断を一文で書く（何を選び、何を捨てたか）
2. その判断が成立していれば必ず現れる量を1つ挙げる（観測対象）
3. その量を外から測る手段を1つ決める（観測方法）
4. 判断が崩れたときに量がどう変わるかを書く（反証条件）
