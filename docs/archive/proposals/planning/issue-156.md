## 3. 企画方針

- 投資推奨にしない。「損失が最初に表面化する場所」を構造で示す。
- 数値はすべて source date を付ける。
- 一次情報・Reuters・Goldman を中心に出典を固定する（Issue の Sources 4件）。
- 再現性のため、データは `project` ごとに表形式で保持する（後述 §5）。

## 4. 損失伝播モデル（台本の骨格）

| 順 | 主体 | 最初に出る損失 | 検証対象 |
|---|---|---|---|
| 1 | Data Center Developer / Owner（Stack / Blue Owl 系） | 建設費・土地・金利の先行固定 | 融資条件、COD 遅延ペナルティ |
| 2 | Project Finance / 銀行 / 債権投資家 | 借換え悪化、ローン価格の下落 | 融資額、取引価格、syndication 状況 |
| 3 | Hyperscaler / Tenant（Oracle） | 支払い延期で一部防御。計算能力の投入遅延は残る | force majeure 条項、支払い延期条件 |
| 4 | AI Operator（OpenAI / Anthropic / xAI 等） | 学習・推論能力の遅延 | 契約上の compute 供給、代替調達 |
| 5 | High-leverage Neocloud | GPU購入費・賃料・金利を抱えたまま稼働遅延 | 個社の契約と電力確保状況（別途検証） |

注意: AI Operator や Neocloud の個別契約は公開情報で確認できない場合が多い。確認できない項目は「不明」と明記する。

## 6. 主要ビジュアル（5点）

1. 計画MW → 電源確保MW → 系統接続MW → 建設完了MW → 実通電MW のファネル図
2. Project Jupiter の契約・資金・電力フロー図（Oracle / Stack / 銀行団 / Bloom / Energy Transfer）
3. 通電遅延1年で誰に何が発生するかの損失伝播図（§4 を図化）
4. 2027年米国DC: 95GW 容量 / 66GW 需要 / 50〜60% 期日通りの関係図（10月改定を反映するか決めてから作成）
5. AIインフラのボトルネック遷移: GPU → HBM → DC → 電力 → 送電 → 変圧器 → ガス → 水 → 許認可 → 金融

図解は既存の drawio など図解ツールを使う方針に従う。

## 7. 台本（5〜10分）の構成案

1. フック（0:00〜0:40）: 「AIデータセンターは建てれば儲かる、ではない。GPUも建物もある。でも電気が来ない。その瞬間、誰が金を失うのか。」
2. 前提: 計画GWと通電GWの違い（Goldman の予測と予定通り稼働率）
3. Project Jupiter の事実関係（force majeure、融資、ガス許可）
4. 損失伝播（§4 の5段階）
5. 希少性が移る先: energized MW、系統接続済み用地、変圧器、behind-the-meter 発電、ガス供給、冷却、許認可済み用地。企業推奨ではなく価値の移動として説明する。
6. 結論: 「需要」ではなく「通電できる資産」を見る視点。投資助言ではない旨を明記する。
