# Issue #207 企画: シリーズ #07「アーキテクトが数字で守るもの」

対象: GitHub Issue #207（親 Issue #200）
状態: 企画定義のみ。動画の制作・公開・Issue のクローズは行っていない。

## 1. 問いと結論

- 問い: 設計判断、定量化、技術的負債をどう結びつけるか。
- 結論: 技術的負債は「感覚」ではなく、ファイル単位の数字（行数・変更頻度・ガードの有無）で見える化し、閾値を CI に置いて初めて「守られる」。数字のない設計判断は、後から検証できない。

## 3. 3テーマと具体例

### 3.1 定量化: 「大きい」を数字にする

- 論点: 「このファイルは大きすぎる」は主観。閾値を決めて数える。
- 具体例（repo 実測, 2026-10-10 時点）:
  - `git ls-files 'src/*.ts' | xargs wc -l` の合計は 35,370 行。
  - 800 行超の TS ファイルは 6 件: `src/domain/agents/audit.ts`（3,069 行）、`src/scripts/produce_byosan_feature.ts`（1,608 行）、`src/scripts/build_byosan_digest.ts`（1,017 行）、`src/scripts/byosan_daily.ts`（966 行）、`src/domain/byosan/feature_spec.ts`（813 行）、`src/io/core.ts`（804 行）。
  - 800 行の基準はグローバル規約（`~/.claude/rules/common/coding-style.md`「800 max」）に由来する。repo 内のファイルサイズ検査は未実装（`package.json` の `check:merge:fast` に該当なし）。
- 誤用: 行数だけで「悪い」と断定する。大きくても凝集していれば問題ない。
- 次回への接続: #08 で「閾値を config に置き、CI で検査する」形に接続する。

### 3.2 主要指標の耐久性: 数字は変更頻度とセットで読む

- 論点: 1 時点の大きさより、何度も触られているかで負債の利息が決まる。指標は時間で劣化しないか確認する。
- 具体例（repo 実測）:
  - `src/domain/agents/audit.ts` の commit 数は 16 件（`git log --oneline -- src/domain/agents/audit.ts`）。最新は `fcd3d8e`（2026-10-10）。
  - 行数 3,069 行 × 高頻度変更の組み合わせが、レビューとテストの負担が集中する候補。
- 誤用: 1 回の計測値を恒久的な KPI とみなす。`wc -l` の結果は commit ごとに変わるため、計測の時点（commit hash と日付）を必ず併記する。
- 次回への接続: #03（SLO）で「数字の有効期限」を扱う際の前提にする。

### 3.3 技術的負債: 負債を「未ガードの数字」として登録する

- 論点: 負債は TODO ではなく、閾値を超えたまま検査されていない状態として定義する。
- 具体例:
  - 現状: 800 行超のファイルが 6 件あるが、検査はなく、放置されている。
  - 登録方法（提案）: 負債台帳に「ファイル, 計測値, 閾値, 検査の有無, 対応 Issue」を置き、閾値超過を CI で検出する。
- 誤用: 負債台帳を作るだけで満足し、閾値検査を入れない。台帳は更新されず陳腐化する。
- 次回への接続: #05（計測 → 閾値 → alert → action → 検証）の流れに接続する。
